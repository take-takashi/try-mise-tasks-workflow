# プロジェクトの intent

この文書は、設計・実装・提案で迷ったときの判断材料です。明示された要件や上位の指示を優先し、この文書だけでは判断できない点は本人に確認してください。

## 大切にすることと判断基準

### 共通する責務をまとめる

複数のワークフローに共通する処理は、共通のクラスや部品へまとめる方針とする。同じ検証や修正を複数箇所で管理し、挙動に差が生じることを避けたい。

例えば、AI の設定検証・認証確認・CLI 呼び出しは共通の AgentClient に集約する。intent を更新する手順も、通常の会話とインタビューで共有する。

共通化した後も、各ワークフローの工程と実行順は、mise が実行するタスクファイルから追える形にする。

### AI プロバイダーをフラットに差し替えられるようにする

利用者によって契約しているプロバイダーが異なり、時期によって最適な AI モデルも変わるため、特定のプロバイダーに固定せずフラットに差し替えられることを大切にする。

プロバイダー間の差異は共通の AgentClient で吸収し、既定モデルの選択のように複雑さを増やす設定は、明示指定がない限り各 CLI 側へ委ねる方向を優先する。課金方式を不要に縛りすぎない一方で、サブスクと API のどちらを使っているかを意識できることや、意図しない API キーの混入を防ぐことを重視する。

### Issue は変更のフロー、docs はテストで保証されたストックとして分ける

実装・テスト・レビューの起点としては GitHub Issue を使う。一方で、永続的な仕様や判断基準は Issue に閉じ込めず、リポジトリ内の `docs/` へ残す。

機能の仕様やテスト観点は壁打ちの段階で Issue に整理し、実装 PR の中でコードおよびテストと一緒に `docs/` を更新する。これにより、`main` の `docs/` が常にテスト PASS で保証された現在の状態を表す形を保ちたい。

### テスト観点（testent）で実装の確かさを保証する

実装の確かさをテストで保証することを大切にし、機能に対して「正常系・異常系・権限・境界値・障害」の 5 観点（testent）を意識してテストを設計・確認する。

まずは過剰な構造化を避け、軽量な Markdown 形式で小さく試しながら育てる方針とする。

### 途中の承認を挟まず自走し、事後の確認と修正で質を保つ

ワークフローの途中に人間の承認ゲートを挟むと自走の流れが止まるため、AI が最後まで進められる工程は自律的に完走させる方針とする。人間は主にマージ後の結果を確認し、誤りや意図とのズレがあれば修正する。

そのため、自走を前提にするほど、人間が後から経緯と変更内容を素早く把握できる読みやすい Issue や Pull Request を作ることが重要になる。AI が判断できない事項や解消できない指摘に当たった場合は、無理に解決済みにせず、理由を残して人間へ引き渡す。

## まだ決まっていないこと

- `docs/` に記載した機能ごとのテスト観点（testent）を使って `tests/` のテストを検証する戦略が、実運用で無理なく成り立つか（適切な粒度や検証・レビューの具体的な進め方）は今後の試用で確かめる。
